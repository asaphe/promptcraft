# The Twelve Nulls — Results That Look Like Answers

Always-loaded: this file carries no `paths:` frontmatter, so it loads every session exactly like the global `CLAUDE.md` does. It is the long form of the **Evidence > assertion** item in `../../config/global-CLAUDE.md` § Always-on checklist, split out because the list outgrew a checklist bullet — and because it has to fire at the moment a result is *read*, not when a doc happens to be opened.

Every entry below produces output indistinguishable from a real answer. That is the whole problem: nothing prompts you to go look them up, because nothing looks wrong.

**The first null: the query never ran.** Empty output, zero matches and a 404 render identically whether the query found nothing or never ran — a vanished argument, an unquoted glob, the wrong cwd. Confirm the command ran as written and could have returned the opposite.

**The second null: a plausible result that is wrong.** A non-empty result can be as wrong as an empty one. Volume and specificity read as credibility, and neither is evidence — check the result against something that could contradict it, not against your expectation.

**The third null: a correct query over the wrong corpus.** A control proving the search reached the paths it was *given* cannot distinguish a missed pattern from a file list that never held the governing file. Before asserting a negative, state the corpus and derive it from whatever declares where things live (a `CLAUDE.md` subdirectory table, `CODEOWNERS`, an index), not from memory.

**The fourth null: research you stopped too early — and unresolved uncertainty is never the deliverable.** Two failed direct fetches is not an exhausted search; escalate (search, then an empirical test) before a load-bearing fact reaches a doc, commit message, or PR. Writing "couldn't determine this" into a durable artifact ships the cost to every future reader, and an unverified belief that reaches a commit *type* or a PR heading asserts something about the world — `fix` claims a defect existed, so verify the brokenness before choosing the verb.

**The fifth null: a check narrower than the claim it is quoted for.** A probe proves only what it exercised, so the gap opens wherever the tested set is narrower than the asserted one. Removing a normalization step (`.replace`, `.strip`, `.lower`) and testing a sample of plausible values leaves untested exactly the input *classes that step existed to handle* — enumerate those, not a sample, or "behaviour-identical" is a false all-clear published to the user. The same gap reopens from the other side when a repo ships an authoritative checker and you re-derive its predicate in another engine: the reimplementation drops the guards the original encodes — a lookbehind, a scoped corpus — so run the checker and widen its corpus rather than rewriting its logic in `grep`. The same narrowness arrives from the outside when a tool hands you the list: a CI annotation, a linter run, a scanner report enumerates the instances *it* detected, never the affected class, so adopting it as the work-list yields a fix that is incomplete exactly where the tool was blind — and it presents as complete, because the warning it was derived from is now silent. Treat such output as the trigger and derive the class yourself (a deprecation annotation naming one action; the real predicate is every pinned action's declared runtime). The narrowness escapes probing altogether once the claim is *authored* rather than tested: "the one genuine fail-open of the three", "both halves are asserted", "every gate has a case" are measurements, and quantifying over the instances you happened to notice publishes your blind spot as a fact — in a doc it becomes the next reader's evidence and outlives the session that guessed it. Derive the class with a command and let the count be the evidence; a claim carrying a number needs one behind it.

**The sixth null: an assertion that compares against the constant under test.** `assert claims["exp"] - claims["iat"] == JWT_TTL_SECONDS` passes for every value `JWT_TTL_SECONDS` could hold, and `assert code == EXIT_DRIFT` passes after any renumbering — the check moves with the thing it is checking. Wherever the value is a **cross-file or cross-system contract** — an exit code another process branches on, a `kid` the identity provider pins, a wire-format field name — assert the literal, and pin the constant to that literal in a second line so a rename fails loudly instead of silently agreeing with itself. The same shape hides inside a library's own API: `jwt.decode(tok, options={"verify_signature": False}, audience=X)` looks like it verifies `audience`, and PyJWT skips that check entirely when signature verification is off, so the kwarg reads as an assertion while testing nothing. Mutation is what exposes all of these — flip the constant, re-run, and require the suite to go red; a test that stays green *is* the finding. And when you fix one, re-read the enclosing function before moving on: this shape clusters, and fixing the instance you were shown while an identical one sits two lines below is the class-enumeration miss in its cheapest-to-avoid form.

**The seventh null: a negative claim about capability, inferred from silence.** "Nothing detects this", "there is no alert for that", "no one owns it" are claims about the world, and they are characteristically made from the wrong evidence: an outage that ran unnoticed for two days measures *attention*, not *instrumentation* — the monitor may exist and route somewhere nobody reads. The cost lands late and lands large, because the usual next step is to propose building the missing thing, and a proposal to rebuild what already exists survives every review that examines the design rather than the premise. Enumerate the mechanism before proposing the replacement — the monitor list, the scheduled jobs, the owning team's runbook — and say which you actually read. This is the third null aimed at a system instead of a corpus, and it fails the same way: the query never ran. The same shape arrives *inherited* rather than inferred, and aimed at yourself: "the classifier denies this", "you don't have permission for that", carried in from a handoff or a prior session's conventions block. That one fails in the costlier direction, because it abandons authorized work instead of merely skipping a check — and a non-mutating probe usually settles it in one command.

**The eighth null: a migration's own search counts its successes as failures.** When replacing A with B, the string for A is usually a *substring* of B — `pip install` sits inside `uv pip install`, `http://` inside a proxy URL that already fixes it, a deprecated import inside the shim that wraps it. The scan then reports every already-migrated call as outstanding work, and the number is wrong in the alarming direction, so it never feels like a null: an inflated backlog reads as diligence and gets published before anyone checks it. Exclude the destination form explicitly, then reconcile the two counts — total minus already-migrated must equal the remainder you are claiming — before quoting either. The same arithmetic exposes the mirror-image error, where a pattern narrow enough to miss the old form under-reports the work left.

**The ninth null: an instruction you believe you executed.** "I already removed that", "that was handled earlier" is a claim about an artifact, sourced from your own memory of intending it — and memory of an intention is indistinguishable from memory of an action. It is the second null aimed inward, and it costs more than the others because the user has usually stopped checking: they asked once, you said done, and the artifact is discovered intact much later by them rather than by you. Re-read the file before reporting anything done, and treat the phrase "I already told you to" as evidence a verification was owed and skipped, never as a prompt to explain why you thought otherwise.

**The tenth null: a summarized answer, mistaken for a citation.** Any tool that answers a prompt *against* a source — a fetch-and-summarize tool, a search wrapper, a subagent asked "what does X say?" — hands back model prose, not the source. It can invent quotes, version numbers and section names that read exactly like citations, and it does so most convincingly when the invention confirms what you expected, which is precisely when you stop checking. The cost lands late, because the fabrication is usually republished: "verified against the official reference" reaches a commit message, a PR body or a ticket, where it becomes the next reader's evidence. Fetch the raw file and quote it, or corroborate against something in-repo, before any such fact is load-bearing — and note that in-repo corroboration is often *stronger*: a sibling repo's own usage and its comment naming the upstream issue beat a doc page, and were sitting there the whole time.

**The eleventh null: a timestamp read as a state.** A creation time is not a status. `createdAt` on a queued job, `startedAt` on a run, `LastModified` on an object — each records when the row entered the list, never what it is doing now, and a listing that mixes finished and pending rows renders both identically. Subtracting it from the clock yields an age that reads as time-in-state, and is one only for the rows that never progressed, so the arithmetic is correct while the claim is false. This one fails toward alarm rather than reassurance, which is why it gets published rather than caught: an invented twenty-minute backlog sounds like diligence and triggers an investigation, where the real figure was six minutes and a single row. Read the state field the row actually carries, and count the rows currently in that state rather than measuring the oldest one. The same subtraction fails a second way, in the *zone* rather than the field: an API timestamp is in the source's zone, not yours — a forge's `createdAt` is UTC while a local `date` is not — so the arithmetic is exact and the answer is off by the offset, silently, with no malformed output to notice. It fails toward alarm in the same direction: a run two minutes old reads as three hours stale, which then seeds a diagnosis of the wrong problem. Compare in one zone and say which zone the claim is in.

**The twelfth null: a capability derived instead of exercised.** A permission set, an RBAC binding, a scope list — anything read out of a declarative artifact to predict what a consumer may do — is a hypothesis, not a finding. The artifact enumerates the *resources that exist*; authorization is spent on the *API calls the consumer issues*, and nothing in the artifact names those. The gap is invisible precisely because the derivation feels like evidence: it is specific, it cites real resource types, and it is wrong in the one dimension it never modelled. Running it yourself does not falsify it either, because you run as an administrator and the consumer does not. Two things actually settle it — exercise it under the real identity and read the denials, or diff against a grant already proven against the same resources — and each denial surfaces only one layer, since a run aborts on the failures it hits and leaves everything behind them untested. Budget for iterations rather than one pass.

## The control probe is the general defense

Before any command's output drives a claim, ask what it would print if it had silently failed. If that looks the same as the result you got, run a control that MUST produce output.

**A silent control is ambiguous, not diagnostic.** It means the command is broken *or* the control is, and those are indistinguishable from the output. A control keyed on something merely believed to be present fails for its own reasons and indicts the wrong thing. Choose a control whose expected output is known independently, and prefer running it in the **same invocation** as the real target — one scan over `<real paths> <known-positive fixture>` proves in a single result both that the command fired and that the real paths are clean.

**An edit to a guard is not verified by reading it back.** A hand-transcribed patch can drop a line and still parse: the syntax check passes, the diff reads correctly, and the predicate is silently wrong — a fail-open in the control you were hardening, which is strictly worse than the gap you set out to close. Prove an edited guard with the three controls whose verdicts are known in advance: one case it must block, one it must allow, and one where its input is unavailable so it must fail closed.

Shell constructs that produce these nulls by construction: `shell-traps.md`.
