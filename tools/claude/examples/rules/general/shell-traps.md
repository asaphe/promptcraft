# Shell Constructs That Return a Confident Wrong Answer

Always-loaded: this file carries no `paths:` frontmatter, so it loads every session. It is deliberately not part of `../../docs/bash-patterns.md`, because these have to fire at the moment a command is *written*, not when a doc is read — every one of them produces plausible output instead of an error, so nothing prompts you to go look them up. Command-composition patterns that fail *loudly* stay in `bash-patterns.md`, which is read on demand. Two bullets below overlap that doc on purpose, for the same reason.

**The control probe is the general defense.** Before any command's output drives a claim, ask what it would print if it had silently failed. If that looks the same as the result you got, run a control that MUST produce output — and pick one whose expected output is known independently, because a silent control is ambiguous rather than diagnostic. Full treatment, including why the control belongs in the same invocation as the real target: `evidence-nulls.md` § The control probe is the general defense.

- **An unmatched glob in zsh leaves the literal pattern** — `ls /tmp/nope-*.jsonl` falls through to listing the *cwd*, so a count of that output reports files that don't exist. Verify with `find -L <dir> -maxdepth 1 -name '<pattern>'`.
- **zsh does not word-split unquoted parameter expansions** — `set -- $pair` sets only `$1` (the whole string); the same line works in bash. Under `set -u` it errors; without it the loop silently processes half the data. Use `while IFS=' ' read -r a b` or `${=var}`. The same trap eats a captured **file list**: `scanner -- $FILES` hands all N names over as one argument, and a per-path tool (`perl`, `grep`) then emits a single `Can't open ...` line and **exits 0** — which reads as a clean scan of every file. Pipe it instead: `printf '%s\n' "$FILES" | tr '\n' '\0' | xargs -0 scanner --`.
- **`find /tmp ...` returns nothing when `/tmp` is a symlink** (macOS → `private/tmp`) — `find` does not follow a symlinked start point. Use `find -L /tmp/` or a trailing slash.
- **`diff` proves content equality, never identity** — comparing a file to itself reports IDENTICAL, so `diff` can never establish that two paths are distinct objects, and `ls -l <file>` is blind to a symlinked *parent* directory. Before any "these are two copies" claim, compare inodes: `stat -f %i <a> <b>` (BSD) or `stat -c %i <a> <b>` (GNU).
- **A pipeline's exit status is its last command's** — `cmd | head && echo OK` takes the OK branch unconditionally, and `$?` after `cmd 2>&1 | tail -5` reports `tail`'s status rather than `cmd`'s. Both read as a pass when the command actually failed, which is the usual shape when checking whether a gate succeeded. Read the real status from `${pipestatus[1]}` (zsh) or `${PIPESTATUS[0]}` (bash) — not interchangeable, and the wrong one expands to empty instead of erroring — or drop the pipe and capture the output to a variable. The same status reaches you laundered when the command is backgrounded: a completion notification reporting `exit code 0` reports the **last** command in the chain, so `gh run watch … | tail -5; echo "exit=$pipestatus[1]"` notifies success on the strength of the `echo`, and a red CI run announces itself as green. A notification's exit code is never a verdict on a command that was not last — open the output file and read the status you actually printed.
- **An unquoted shell variable inside a `jq` filter** breaks the program; jq prints nothing, and empty output reads as "no matches". **`gh --jq` is not `jq`** and fails the same way from the other end: it accepts exactly one filter and rejects `--arg`/`--argjson` with `accepts 1 arg(s), received N` on *stderr*, so a loop that shells out per item prints a tidy negative for every one while no answer was ever fetched — six `MISSING` lines about required status checks that were all in fact green. Pipe to real `jq` when the filter needs a variable. The general tell, whichever form bit you: a per-item loop returning the **same** negative for every item is itself the signal, because a genuine check rarely fails identically across unrelated inputs.
- **`jq`'s `//` catches only `null` and `false`, never `""`** — `.conclusion // "PENDING"` looks like it labels an unfinished check, but a forge reports a pending check as `conclusion: ""`, so the fallback never fires and the tally comes back with a blank-named bucket. A wait-loop keyed on the word `PENDING` then exits on its first pass and reports in-flight CI as settled. Test the emptiness explicitly — `if (.conclusion // "") == "" then "PENDING" else .conclusion end` — and make the loop's own predicate provably able to emit the sentinel before trusting its absence. **`gh pr checks` fails the same way one level up**: it renders only the checks that have *reported*, so an in-flight one is absent from the table rather than listed as pending — fifteen green rows and no sign of the sixteenth still running, which reads as a complete green run. Read the check-runs API grouped by status instead, and confirm each required context by name rather than trusting the aggregate.
- **A scripted in-place edit that matches nothing still exits 0** — Python's `str.replace`, `sed 's/a/b/'`, and a `jq` assignment down a path that doesn't exist each rewrite the file with its original bytes and report success. A trailing `print("updated")` attests that the *script* ran, never that the edit landed, so quoting it back as confirmation launders a no-op into a completed change. Verify against the artifact instead: re-grep the old text and require zero hits, assert the replacement count, or use an editor that errors on no-match (Claude Code's `Edit` tool does — prefer it over a script for one-off edits precisely because a failed match is loud). The risk is symmetric and the over-match half is quieter, because it also exits 0 *and* changes the file: replacing a bare token like `285` across a styled document hits the CSS hex `#5f7285` exactly as readily as the stat you meant, and the corruption is invisible until something renders. Count the *contexts* of a match before replacing, not just the occurrences, and anchor on surrounding text rather than the bare token. **And when a scripted edit is followed by a mutating command in the same invocation, join them with `&&`** — separated by newlines the second command runs whether or not the edit landed, so a no-op edit is followed by a real `terraform apply` whose `Apply complete! Resources: 0 added, 0 changed, 0 destroyed` is indistinguishable from a genuine converged apply. Read the anchor out of the file immediately before writing the replacement rather than recalling its shape; a remembered list ordering is the usual reason the match count comes back zero.
- **A same-second edit-and-revert can still execute from a stale `.pyc`** — Python invalidates bytecode on the source's `(mtime, size)`, and a mutation test leaves both unchanged when it rewrites a file to an equal-length mutant and restores it inside one clock tick. The restored source then never runs: the suite reports the *mutant's* result, so correct code reads as broken, and in the other direction a mutation reads as caught when it was only cached. The workflow that most reliably produces same-second rewrites of identical-length files is exactly the one whose verdict this destroys. Clear `__pycache__` between every step, and prove a restore with `md5`/`shasum` against a pre-mutation copy — a passing suite cannot tell a good restore from a stale cache.
- **`grep` is line-scoped, so a pattern that spans a newline cannot match** — over multi-line content (HTML, formatted JSON/YAML, a wrapped log record) a phrase that happens to wrap returns zero hits, and zero hits reads as "already fixed" rather than "wrong tool for this corpus". Verified on a 93 KB HTML file: a stat that was demonstrably present came back absent from `grep`, and the same pattern found it immediately under Python's `re` with `DOTALL`. Match multi-line formats with an engine that can cross lines, and never let a `grep` null alone establish that something is gone.
- **A line-scoped tool cannot verify a claim whose unit is not a line** — the trap above is one instance; two more bite routinely. `grep -c` with an alternation counts matching *lines*, so it can never confirm that N distinct patterns are all present: one line matching one alternative returns `1`, which reads as a pass for all N. And `grep -v <marker>` over a multi-line block — a YAML `command: >-`, a here-doc, a wrapped value — excludes only the marker's own line and leaves the rest of that same logical block in the output, where a guard whose opening line was filtered away then reads as absent. Loop and print per pattern when checking N of them, and read the whole block when the unit is a block.
- **A runtime-semantics probe run on the wrong interpreter answers confidently and wrongly** — a system `python3` is routinely several minor versions behind the one a project targets, and that gap is exactly where the semantics being probed changed: `datetime.fromisoformat` rejects a trailing `Z` on 3.9 and accepts it on 3.12, so one probe returns opposite verdicts with no error either way. Run it under the project's interpreter (`uv run --python 3.12 --no-project python -c ...`) and print `sys.version` inside the probe's own output, so a mismatch surfaces in the result rather than silently in the conclusion drawn from it.
- **A URL is a glob pattern until you quote it** — `?` and `*` are zsh metacharacters, so `gh api "repos/o/r/contents/f.yml?ref=$SHA"` works while the same line unquoted expands to nothing and the command runs against a mangled or absent argument. It fails to **empty**, not to an error: three consecutive fetches returned zero bytes and read as "this file declares no such field" — the exact fact the task turned on. Quote every URL carrying `?` or `&`, and when a fetch feeds a claim, print a byte count beside the grep so an empty body is visibly empty rather than a confident negative.
- **The `Glob` tool's `pattern` does not expand `~`** — silent zero-match even when files exist. Pass an absolute path, or use Bash.
- **A failed `cd` does not stop the next command from running against the wrong directory** — `cd <missing> && git worktree add ...` (or any `;`-chained form) creates the artifact in the *session's* repo. Always pass `git -C <repo>` explicitly rather than relying on a preceding `cd`.
- **A git ref pattern is pathname-aware: `*` stops at `/`** — `git for-each-ref 'refs/pull/*'` matches nothing, because `refs/pull/N/head` is two segments deep; the same wildmatch rule governs `git push --delete` refspecs and `--exclude`. Zero output reads as "already gone", so a deletion loop over it reports success having done nothing. Use the prefix form (`refs/pull/`) and confirm with a count before and after.
- **An `echo` beside a command asserts a verdict the command never produced** — a marker line like `echo "(no output above = zero references)"` runs unconditionally, so it prints its conclusion whether the command matched nothing, matched everything, or never ran at all. The reader then sees a formatted verdict sitting directly beneath contradicting data and believes the verdict — worst exactly where such markers get added, which is a blast-radius or consumer check run immediately before a deletion. Print the evidence and *derive* the verdict from it — a match count, an exit status, a `[ -s "$out" ]` test — so the line cannot render when the claim is false. Same family as the `print("updated")` trap above: an authored confirmation attests that your script ran, never what it found.
- **A script handed to the user to run later must re-derive every session-scoped path at run time** — a secret cache, a temp file or a worktree path captured while authoring can be swept between the turn that wrote the script and the turn that runs it; the script then dies on its first line or, worse, reads a stale artifact and reports a result computed from nothing. Resolve such paths *inside* the script by re-invoking whatever produced them, and fail closed with a named error when resolution comes back empty, so the user sees `could not fetch X` rather than a clean-looking probe result.

Corollary for any git subcommand that writes: `worktree add`, `branch`, `checkout`, and `commit` all act on the cwd's repo when no `-C` is given, and none of them error when that is the wrong repo.
